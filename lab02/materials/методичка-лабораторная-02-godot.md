# Лабораторная работа №2. Платформер в Godot: где заканчивается движок и начинается игра

**Курс:** «Архитектура компьютерных игр» · НИУ ВШЭ · неделя 2
**Формат:** семинар (80 минут) + домашнее задание №2
**Материалы:** учебный комплект платформера (`platformer-teaching-kit.zip`) — пять проектов Godot с этапами 00–04.

---

## 1. Что понадобится

- **Godot 4.x** (обычная сборка, без .NET — работаем на GDScript). Скачать: https://godotengine.org/download — Windows, macOS и Linux; установщика нет, это одно приложение. На Apple Silicon берите обычную macOS-сборку, она нативная. Если macOS блокирует первый запуск: «Системные настройки → Конфиденциальность и безопасность → Всё равно открыть».
- **Комплект платформера**, распакованный в обычную папку (не открывайте проект внутри ZIP). Сохраните исходный архив как запасную копию.

## 2. Подготовка (10 минут, до начала опытов)

1. Откройте Godot → в менеджере проектов нажмите **Import** → выберите `godot/04_coin/project.godot` → **Edit**. Дождитесь окончания импорта.
2. Запустите проект кнопкой ▶ (или F5 / Fn+F5 на Mac). Сначала кликните мышью в игровое окно, чтобы оно получило фокус.
3. **Проверьте исходное состояние** — это эталон, с которым сравниваем все изменения:
   - A / D или стрелки — движение, пробел — прыжок;
   - подберите монетку: она исчезает, счёт становится 1;
   - нажмите R: монетка возвращается, счёт становится 0.
4. Если что-то не так на этом шаге — проблема в установке, а не в ваших правках. Зовите преподавателя сейчас, а не после опытов.

## 3. Ход работы: четыре опыта

Правило каждого опыта: **сначала записываете прогноз, потом меняете, потом записываете наблюдение.** После каждого опыта возвращайте исходное значение.

### Опыт 1. Высота прыжка (параметр игры)
1. Остановите игру, выберите Player в сцене World.
2. В Inspector измените `Jump Velocity`: −560 → −720.
3. Запустите, сравните, верните −560.
*Прогноз: число стало меньше — прыжок будет выше или ниже?*

### Опыт 2. Клавиша прыжка (настройка движка)
1. Project Settings → Input Map → действие `jump`.
2. Добавьте клавишу J, удалите Space.
3. Проверьте, затем восстановите Space.
*Прогноз: потребуется ли менять условие прыжка в player.gd?*

### Опыт 3. Коллайдер (физическая геометрия)
1. Откройте этап `02_jump`, сцену Player.
2. У CollisionShape2D включите `Disabled` и запустите проект.
3. Наблюдайте, верните `Disabled = Off`.
*Прогноз: что произойдёт с рисунком героя? с его поведением?*
*Подсказка для наблюдения: Debug → Visible Collision Shapes показывает границы тел.*

### Опыт 4. Вторая монетка (повторное использование сцены)
1. В этапе `04_coin` продублируйте Coin в сцене World (Ctrl+D).
2. Поставьте новый экземпляр в точку (490, 304).
3. Запустите, соберите обе монетки: ожидаемый счёт — 2.
4. Найдите: сигнал `collected` в coin.gd и подписку на него в world.gd.
*Прогноз: знает ли coin.gd, где расположен счётчик?*

### Финал. Заглянуть внутрь движка
Откройте в браузере исходник подсистемы ввода Godot: `github.com/godotengine/godot` → `core/input/input_map.cpp` → найдите `action_add_event`. Ответьте: что проверяется до добавления события в список, и зачем? Соотнесите с опытом 2: почему одна и та же привязка не добавляется дважды.

## 5. Критерии зачёта (10 баллов)

| Критерий | Баллы |
|---|---:|
| Игра запускается, все четыре опыта выполнены и задокументированы (прогноз + наблюдение) | 4 |
| Правильно разделены уровни изменений: правило игры / настройка движка / исходники движка | 2 |
| Разбор InputMap: назван файл, найдена проверка дубликата, объяснена её роль | 2 |
| Ответы на вопросы показывают понимание границы «движок — игра» (а не пересказ интерфейса) | 2 |

Изменение цвета или картинки само по себе зачётом не считается — объяснение обязательно.

## 6. Домашнее задание №2 (включает эту лабораторную)

**Срок:** к занятию недели 3. **Вес:** входит в компонент «Домашние задания» (0,30 итоговой).

1. **Отчёт по опытам** (раздел 4 выше).
2. **Карта модулей v0.1 сквозного проекта.** Для вашей игры из ДЗ №1 составьте карту из 4–6 модулей. Для каждого: ответственность, вход (публичная операция), разрешённые зависимости. Отдельно отметьте, что предоставляет выбранный движок. Не называйте каждый узел сцены модулем автоматически.
   *Пример записи:* «Контроллер героя получает действия move_left / move_right / jump, задаёт скорость тела и использует API столкновений. Он не обращается к тексту счёта».
3. **Одно архитектурное решение письменно:** требование → выбранная граница → причина → цена изменения. *Пример:* «Нужно переназначать клавиши. Используем имена действий Input Map. Платим поддержкой таблицы привязок, избегаем прямой проверки Space в логике».
4. **Использование ИИ** — одной фразой: с чем помог ассистент и как вы проверили результат.
